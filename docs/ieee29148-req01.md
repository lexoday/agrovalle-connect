# Especificación de requisitos IEEE 29148 — HU-01 Registro de Agricultores

Norma: ISO/IEC/IEEE 29148:2018. Redacción prescriptiva con cláusulas "El sistema deberá...".
Historia origen: HU-01 (BACKLOG.md), Sprint 1, 5 SP.

## 1. Propósito y alcance

Permitir que un agricultor del Valle del Cauca se registre en AgroValle Connect con sus datos personales y de finca, para poder publicar sus cosechas.

## 2. Partes interesadas

- Agricultor (productor): usuario que se registra.
- Product Owner: valida el alcance.
- Equipo de desarrollo: implementa y verifica.

## 3. Requisitos funcionales

| ID | Requisito | Criterio de verificación | Trazabilidad |
|---|---|---|---|
| RF-01 | El sistema deberá registrar un productor con nombre, correo, cédula, municipio y contraseña. | Respuesta 201 con los datos registrados. | `AuthControllerTest.registroExitoso`, `ProductorServiceTest.registraYCifraContrasena` |
| RF-02 | El sistema deberá aceptar el campo opcional nombre de finca. | Registro exitoso sin nombre de finca. | `ProductorServiceTest.registraYCifraContrasena` |
| RF-03 | El sistema deberá rechazar un registro cuya cédula ya exista, con código 409. | Respuesta 409; no se guarda ningún registro. | `AuthControllerTest.cedulaDuplicada`, `ProductorServiceTest.rechazaCedulaDuplicada` |
| RF-04 | El sistema deberá rechazar un registro cuyo correo ya exista, con código 409. | Respuesta 409; no se guarda ningún registro. | `ProductorServiceTest.rechazaCorreoDuplicado` |
| RF-05 | El sistema deberá rechazar con código 400 un registro sin campos obligatorios o con correo inválido. | Respuesta 400 con mensaje de campo. | `AuthControllerTest.campoVacio` |
| RF-06 | El sistema deberá responder 201 Created con encabezado `Location` y sin devolver la contraseña. | Encabezado `Location` presente; ausencia del campo `password`. | `AuthControllerTest.registroExitoso` |

## 4. Requisitos no funcionales

| ID | Requisito | Atributo ISO/IEC 25010 | Verificación |
|---|---|---|---|
| RNF-01 | El sistema deberá almacenar la contraseña únicamente como hash BCrypt. | Seguridad (confidencialidad) | `ProductorServiceTest` verifica `passwordEncoder.encode` |
| RNF-02 | El sistema deberá persistir el registro en la tabla `usuarios_productores` de PostgreSQL. | Fiabilidad (integridad) | `schema.sql` con restricciones UNIQUE |
| RNF-03 | El sistema deberá responder en menos de 2 segundos en condiciones normales de uso. | Eficiencia de desempeño | Pendiente de medición |

## 5. Restricciones y brechas identificadas

- No hay longitud mínima de contraseña definida. Requiere decisión del Product Owner.
- El campo municipio acepta cualquier texto; no se restringe a los municipios del Valle del Cauca. Pendiente.
- RNF-03 aún no tiene prueba de desempeño.

## 6. Matriz comparativa: IEEE 29148 frente a BDD

| Criterio de ingeniería | Especificación formal IEEE 29148 (SyRS) | Historia de usuario ágil + BDD |
|---|---|---|
| Propósito y enfoque | Documentación prescriptiva, exhaustiva y estable para acuerdos contractuales. | Carta de conversación ágil, ejecutable y enfocada en el valor continuo para el usuario. |
| Sintaxis y estructura | Cláusulas normativas con ID ("El sistema deberá..."). | "Como [rol] quiero [acción] para [beneficio]" y escenarios Given-When-Then. |
| Validación y pruebas | Matriz de trazabilidad requisito → caso de prueba. | Escenarios traducibles directamente a métodos `@Test` en JUnit 5. |
| Gestión del cambio | Requiere control formal de cambios (CCB) y revisiones rígidas. | Refinamiento continuo (Backlog Grooming) al inicio de cada Sprint, por el Product Owner. |

### Ejemplo de equivalencia

- BDD: *Dado* un correo ya registrado, *cuando* un agricultor se registra con ese correo, *entonces* el sistema responde 409.
- IEEE 29148: RF-04 — El sistema deberá rechazar un registro cuyo correo ya exista, con código 409.

Conclusión: la norma aporta trazabilidad y restricciones verificables que el BDD no formaliza; el BDD aporta una especificación ejecutable que se traduce directamente a pruebas. Ambas se complementan en este proyecto.
